# 240 FPS、8 核 CPU 与 GPU 优化设计

## 目标

在不改变玩法规则、战斗判定、随机数顺序、存档格式和现有素材内容的前提下，把前台游戏的原生呈现上限提升到 240 FPS，并针对 8 核 CPU 减少主线程渲染准备开销。GPU 侧只迁移经过测量证明值得的视觉工作，继续使用 raylib 6.0 与 OpenGL 3.3。

本设计的核心是“60 Hz 权威逻辑 + 最高 240 Hz 输入采样和原生呈现”。渲染帧必须使用插值后的不同位置与视觉状态，不是把同一张 60 Hz 画面重复显示四次。

## 定义与边界

- **权威逻辑 tick**：战斗、AI、碰撞、伤害、掉落、随机数、房间状态和存档提交继续固定为 60 Hz。
- **呈现帧**：输入采样、相机、变换插值、视觉动画准备和 GPU 提交以最高 240 Hz 运行。
- **原生 240 FPS**：垂直同步关闭且硬件允许时，程序每秒生成并提交最多 240 个有独立插值状态的画面。垂直同步开启时，实际显示帧率受显示器刷新率限制。
- **素材动作帧**：角色或技能图集中的独立绘制帧。提高呈现率不会凭空补出素材帧；素材动画仍按自身时间线切帧，位置、相机和程序特效可以在相邻逻辑 tick 间平滑更新。
- **8 核优化**：主线程负责权威逻辑和所有 raylib/OpenGL/音频调用，最多创建 6 个常驻工作线程；主线程可参与纯 CPU 准备工作，并至少给操作系统、音频和显卡驱动保留一个执行资源。

## 当前基线与机器约束

已有本地性能记录显示，普通材质场景约为平均 120 FPS、P99 约 9.25 ms、1% low 约 108 FPS；30 怪物压力场景约为平均 66 FPS、P99 约 20 ms。这些记录早于本轮优化，必须在当前提交上重新采样，不能直接作为最终对比基线。

当前开发机为 Intel Core i7-13620H（10 核、16 逻辑处理器）与 RTX 4060；当前显示输出为 1920×1080、144 Hz。因而：

- 开启垂直同步时，本机可见输出通常封顶约 144 FPS，这不代表 240 FPS 调度失败。
- 240 FPS 性能验收使用关闭垂直同步的固定场景；观感验收同时覆盖 144 Hz 垂直同步模式。
- 8 核适配不能以当前 10 核机器可运行作为唯一证据，必须验证 1、2、4、6 个工作线程配置。

## 总体架构

每个前台帧按以下阶段运行：

1. 主线程采样 raylib 与 Win32 补充输入，把按下/释放边沿保留到下一个权威 tick 消费。
2. 固定步长累加器按现有 60 Hz 规则执行零次或多次权威 tick，并保留前一份与当前一份只读呈现快照。
3. 根据 `alpha = accumulator / fixed_step` 计算呈现状态；只读快照和版本号交给稳定缓存及帧准备线程池。
4. 工作线程只生成固定容量的视图数据和绘制命令；主线程按稳定键合并。
5. 主线程按深度顺序提交 raylib/rlgl 绘制，合并相邻且材质状态兼容的命令。
6. `EndDrawing()` 完成呈现与帧率限制。前台目标为 240 FPS；开启垂直同步时采用显示器实际刷新节奏。

逻辑 tick 落后时沿用受限追帧策略，禁止无限补 tick 造成“死亡螺旋”。不得为了追求显示数字而跳过权威 tick、缩短技能持续时间或改变伤害时序。

## 帧率、输入与插值

窗口成功初始化后设置唯一的 `SetTargetFPS(240)`。调用必须位于 `InitWindow()` 成功之后，不能在多个分支反复设置。现有垂直同步选项保持有效：垂直同步开启时由显示器节奏限制实际呈现，关闭时由 240 FPS 上限限制，禁止无上限忙跑。

输入在每个呈现帧采样，数字键、J/K/L、WASD 等离散输入的边沿使用固定容量锁存结构保存。零 tick 的呈现帧继续保留边沿；同一呈现帧执行多个权威 tick 时，`pressed/released` 只交给第一个允许接收玩法输入的 tick 并恰好消费一次，`held` 状态交给该帧的全部 tick。这样即使按键发生在两个 60 Hz tick 之间也不会丢失或在追帧时重复触发。输入采样本身不得从工作线程调用 raylib 或 Win32 API。

暂停菜单、背包、死亡门禁或失焦阻断玩法输入时，当帧中与 UI 有关的边沿只交给 UI，其余玩法边沿立即丢弃，不能延迟成恢复后的攻击、技能或移动。非失焦门禁不伪造释放，解除后 `held` 可以按当前物理状态继续；失焦时清除全部锁存边沿和按住状态，并要求每个键先被观察到释放才重新武装，恢复后必须有新的物理按下才产生输入。

呈现快照保存前一 tick 和当前 tick 的位置、朝向及可插值视觉参数。普通实体采用确定性的线性插值；瞬移、换房、复活、死亡切换等带有不连续标志的状态直接吸附到当前值，禁止跨房间拉出残影。碰撞盒、伤害点和存档位置永远使用当前权威状态，不能使用插值结果。

传统插值会保留一个固定 tick 的历史，因此本阶段先测量按键到下一可见反馈的延迟。只有测量证明玩家关键动作仍明显受 60 Hz 等待影响时，才允许在后续独立设计中对玩家或关键碰撞采用 120 Hz 子步；不得把全部游戏逻辑提升到 240 Hz，也不得让下一节有界的应急视觉外推进入或替代权威判定。

保持现有玩法语义：窗口最小化或失去焦点不自动暂停权威逻辑。后台循环通过独立的低频等待以 60 Hz 上限继续执行权威 tick，不重复调用 `SetTargetFPS`，并跳过不必要的 240 Hz 帧准备、让工作线程在无任务时休眠；显式暂停菜单仍冻结玩法。重新获得焦点时只丢弃操作系统挂起造成的、超过既有追帧上限的墙钟积压，绝不补跑旧 tick，也不清除已经正常执行的权威时间。

## 卡顿预测与应急插值帧

增加一个只影响呈现的 `FrameDeadlineGuard`。它使用最近 120 个前台帧的固定容量阶段耗时、下一帧预计权威 tick 数、可见实体/特效数量和当前工作队列完成率估算 CPU active time。连续两次估计达到 3.50 ms，或当前帧准备到 3.20 ms 仍未发布完整结果时，进入应急模式；连续 30 帧估计低于 3.00 ms 且没有准备超时后退出。进入和退出阈值分离，避免在临界点反复切换。

应急模式不生成新的玩法状态，也不是 DLSS/AFMF 式 AI 造帧。主线程不等待逾期的纯 CPU 帧准备，而是复用最近两份**已经完整发布**的绘制命令生成轻量插值帧。每条可复用命令都携带稳定身份 `(room_generation, entity_kind, stable_slot, entity_generation, subcommand_kind, emission_index)` 和不含连续变换的兼容签名；两帧按稳定身份配对，禁止按数组下标盲配。

应急插值/外推白名单只有世界位置、相机位置和显式标记为连续的旋转。速度只用于计算白名单字段，不作为权威结果。可见性、层级/深度、源矩形、动画/攻击/技能帧、命中闪光、伤害数字、危险预警、HUD、颜色/透明度、材质/纹理/着色器代际和混合状态全部固定为最新完整帧；两帧的命令集合或任一离散兼容签名不同，就禁止对应命令外推。短时外推最多覆盖两个呈现帧且总时间不超过 8.33 ms；超过上限时保持最新完整视觉状态并记录硬卡顿，禁止无限外推、穿墙或显示幽灵命中。

房间切换、复活、死亡、瞬移、实体拓扑变化、攻击/技能/命中等离散展示版本变化、材质代际变化或没有两份兼容完整帧时禁用应急复用，直接使用独立输出槽的串行完整路径。恢复正常时只接收代际和兼容签名均匹配的完整结果，视觉纠偏最多跨两个呈现帧且不进入碰撞、伤害、RNG 或存档。应急帧仍由主线程通过现有 OpenGL 3.3 路径提交，不创建独立渲染线程，也不要求 Compute Shader。

帧准备采用四个固定 `FramePrepSlot`，每槽包含不可变输入和独占输出，状态只能按 `free -> running -> complete -> free` 或 `running -> cancel_requested -> free` 转移。两个 `complete` 槽保存应急历史，最多一个槽处于 `running/cancel_requested`，另一个槽保留给主线程串行完整回退；有在途代际时不得再提交第二个异步代际。请求取消后，全部参与工作线程在任务边界确认退出并递减计数，计数归零前输入和输出槽均不得复用。迟到结果只有在未取消、代际与兼容签名仍匹配时才能原子发布，否则整份丢弃；串行回退绝不写入逾期工作线程正在使用的槽。

该机制只能遮住渲染准备或工作线程的 1～2 帧 CPU 尖峰。若主线程阻塞在权威逻辑、系统调度、磁盘、驱动、`EndDrawing()` 或 GPU 上，它无法继续提交画面；计时器必须把这种情况报告为不可遮蔽硬卡顿，禁止虚报为插帧成功。

## 分阶段计时与新基线

先建立固定容量、普通呈现热路径新增零分配的帧计时器，至少记录：

- 输入采样；
- 60 Hz 权威逻辑；
- 快照与缓存更新；
- 并行帧准备和主线程合并；
- 绘制提交；
- `EndDrawing()` 与等待；
- 完整帧时间。

计时样本写入预分配环形缓冲区，每秒或在显式性能报告时汇总平均值、1% low、P95、P99 和最大值。禁止每帧格式化日志、扩容容器或同步读取 GPU 结果。报告明确区分：排除软件限帧和 VSync 等待的 **CPU active time**，以及包含全部等待的 **wall frame interval**，防止把正常等待误判成计算热点。

基线场景使用固定种子、固定分辨率和相同构建配置，至少包含普通房间、30 怪物战斗、96 怪物压力场景、两个主动技能高特效阶段。编译、测试和真实窗口基准串行运行，不与其他高负载任务并发。

## 版本化稳定缓存

在引入多线程前，先消除同一个 60 Hz 状态被最多四个呈现帧重复准备的问题。缓存只保存纯 CPU、可验证失效条件的数据：

- HUD 静态布局由分辨率、语言、字体和界面版本失效；生命、护盾、冷却等动态值单独更新。
- 掉落物布局由房间 ID、掉落版本和相机/分辨率相关版本失效。
- 材质常驻请求由房间、生态、存活怪物类型、装备技能和资源版本失效；请求未变化时不得重复扫描或加载。
- 不依赖插值 `alpha` 的怪物展示基础数据按权威 tick 版本缓存；每个呈现帧只计算位置、相机和当前视觉时间相关部分。

缓存键必须来自单调版本号或完整稳定值，禁止根据对象地址或未初始化内存判断命中。房间切换、读档、死亡继续和分辨率变化必须显式失效。缓存失败或版本不一致时直接走现有串行准备路径，不能显示上一房间数据。

## 8 核帧准备线程池

新增单一固定容量 `FramePrepPool`（最终名称可在实现计划中按现有命名规范调整），生命周期位于 raylib 窗口和音频系统之内：窗口初始化后创建，在 renderer、材质、音频或窗口中任意一个开始销毁前停止并 `join`。部分线程创建失败时也必须停止并回收已经创建的线程，然后整池回退串行。

线程策略：

- 默认工作线程数为 `min(6, max(0, hardware_concurrency - 2))`；`hardware_concurrency == 0` 时使用串行。这里的 1、2、4、6 均指**不含主线程**的工作线程数。普通游戏的诊断覆盖值超出默认可用量时向下夹紧；确定性测试夹具可以显式创建 1/2/4/6 个真实工作线程，即使 CI 因核心较少而短时超订阅，但不能与性能基准并发运行。
- 工作线程常驻并通过条件变量休眠，禁止每帧创建线程、`std::async`、忙等或无界任务队列。
- 小场景低于经基准确定的串行阈值时直接由主线程处理，避免唤醒和同步成本高于收益。
- 主线程在完成权威工作后可以处理一个预先划分的切片，但不能在等待期间调用会改变权威状态的逻辑。

主线程从当前快照复制帧准备所需字段到专用固定容量 `FramePrepInput`，再以代际号发布；不得把包含动态背包等可变数据的 `DungeonSnapshot` 直接借给工作线程。工作线程只读取已发布输入，主线程在该代际屏障完成前不得修改或复用其存储槽。

怪物、掉落和纯视觉特效按稳定槽位划分连续区间，每个线程写入自己的固定容量切片或全局数组的互斥索引区间。最终比较规则复用并固化现有渲染器的完整层级/深度规则；比较结果相同时再按对象种类、稳定槽位和命令发射序号作为固定 tie-break。主线程按该规则稳定合并，禁止按线程完成先后拼接或跨深度全局材质排序。

命令容量由现有 96 怪物、384 投射物、96 危害以及玩家、掉落、技能特效和 HUD 的公开固定上限推导并写入编译期常量；每一项最坏命令放大倍数都有注释与 `static_assert`/容量测试，不能在实现时凭经验任意填写。

每个任务为无分配、无异常传播的有界函数。队列满、线程创建失败、快照版本变化或线程池未启动时，当前帧使用串行准备；禁止丢弃任务后提交半帧。调试构建记录越界与超时诊断，发布构建不得以自旋等待掩盖阻塞。

## 主线程硬边界

下列工作始终留在主线程：

- `CombatWorld`、地下城和房间状态的权威更新；
- AI 决策提交、碰撞、命中、伤害、击飞、掉落和事件顺序；
- RNG 消费、存档编码和双槽提交；
- 全部 raylib、rlgl、OpenGL、窗口、输入和音频公开 API 调用；
- 纹理/着色器加载卸载、材质常驻集变更和最终绘制提交；
- 工作线程结果的稳定合并与容量/版本校验。

本阶段不并行化 AI、战斗 tick 或共享对象池。它们同时读写玩家、投射物、危害、事件、RNG 和固定槽位，收益未经证明且会直接威胁确定性。

## OpenGL 3.3 GPU 优化

当前材质着色器已经在 GPU 完成颜色图/材质图通道混合，主要风险是每个精灵重复切换着色器、纹理和 uniform，引发 CPU 提交开销与批次刷新。因此先优化命令组织，不更换图形 API：

1. 帧准备阶段生成包含深度、图集、颜色纹理、材质纹理、着色器变体和紧凑参数的固定容量绘制命令。
2. 主线程保持原始深度顺序，只把**相邻且状态完全兼容**的命令组成连续 run；不能跨越其他深度对象进行全局材质排序。
3. 状态缓存跳过重复的着色器、纹理和相同 uniform 设置；健康材质路径可使用 raylib/rlgl 的 OpenGL 3.3 批处理能力一次提交相邻 run。
4. 着色器编译、图集缺失、容量溢出或批处理校验失败时，逐对象回退到现有 `DrawTexturePro`/材质绘制路径。

批处理不得改变透明混合顺序、脚底锚点、遮挡、命中提示或材质颜色。禁止为了减少 draw call 把所有对象按纹理全局重排。

只有在 CPU 优化和材质批处理后，性能报告仍证明大量纯视觉粒子消耗显著时，才考虑使用 OpenGL 3.3 可用的实例化或顶点/片元着色方案迁移纯视觉粒子。该路径必须有固定容量 CPU 回退，不能影响伤害、碰撞或随机数，且必须达到本设计的收益门槛。

## 不采用 OpenGL 4.3 Compute Shader

项目当前固定为 OpenGL 3.3。raylib 6.0 的计算着色器与 SSBO 接口只有在 OpenGL 4.3 构建下可用；切换会增加驱动兼容、资源同步和回读风险。当前确认的主要热点是 CPU 重复准备与材质状态切换，不是适合通用计算着色器的大规模独立计算。

因此本阶段明确不切换 OpenGL 4.3，不把 AI、碰撞、伤害或房间生成迁移到 GPU，也不引入 GPU 到 CPU 的同步回读。以后只有独立基准证明 OpenGL 3.3 路径无法达标、目标机器均支持 4.3 且存在可隔离的纯视觉计算负载时，才能重新立项。

## 资源、失败与生命周期

- 延续材质常驻峰值不超过 256 MiB 的约束；现有测量约 226.8 MiB，只剩约 29 MiB 余量。
- 不无条件新增全分辨率多通道后处理。单张 1920×1080 RGBA8 缓冲约 8.3 MiB，4K 约 33 MiB，会快速突破预算。
- 所有帧命令、任务、计时样本和缓存均有编译期或初始化期固定上限。预热后的 FramePrep 调度、缓存命中、命令生成、稳定合并和普通呈现路径的**新增堆分配为 0**；启动、资源加载、存档提交和背包状态变更中的既有动态容器单独统计，不属于该门禁。
- 工作线程只持有代际有效的 `FramePrepInput`；关闭窗口、切换房间和重载资源前必须完成或取消代际并等待线程退出安全点。
- 并行准备不可用时整帧退回串行；GPU 批处理不可用时仅渲染路径退回现有逐精灵方案。回退不得改变权威状态。
- 后台、最小化和暂停状态不保持 240 FPS 忙跑；线程池在无任务时休眠。

## 性能验收与回滚规则

在当前 1080p 开发机、Release 构建、关闭垂直同步且前台运行时，目标为：

- 普通及 30 怪物代表场景平均帧率不低于 230 FPS；
- 1% low 不低于 200 FPS；
- CPU active time P99 不高于 4.17 ms；该值不包含软件限帧或 VSync 等待；
- 没有周期性任务队列积压、普通呈现热路径新增分配、同步 GPU 回读或工作线程忙等。

96 怪物压力场景用于比较可扩展性，不把无法代表正常游玩的极限场景伪装成普通验收；其目标和最终结果在建立新基线后据实记录。144 Hz 垂直同步观感验收要求稳定贴合刷新节奏、无明显微卡顿或输入丢边沿。

平均 FPS 与 1% low 都从关闭垂直同步后的 wall frame interval 计算。每个场景预热后至少采集 10,000 帧；1% low 定义为最慢 1% 帧间隔的算术平均值取倒数。CPU active time 的 P95/P99 单独计算，不能与 wall interval 混用。

每项缓存、并行或 GPU 优化必须在目标场景中至少满足一项：CPU active time P99 改善 10% 以上，或对应阶段稳定减少约 0.5 ms；同时不得让其他代表场景显著退化。未达到收益门槛的复杂路径必须回滚或保持默认关闭，不能以理论收益保留。

## 测试矩阵

实现按 RED → GREEN 进行，至少覆盖：

- 源码/平台测试确认窗口初始化后恰好设置一次 240 FPS 目标。
- 固定步长测试确认呈现频率变化不改变 60 Hz tick 数、技能持续时间、伤害与房间进度。
- 输入锁存测试确认短按发生在 tick 之间仍恰好消费一次，零/多 tick、长按、UI 门禁和切焦点均符合明确消费规则且不会补发旧输入。
- 插值测试覆盖普通移动、相机、瞬移、换房、死亡和复活吸附；插值值不能进入碰撞或存档。
- 缓存测试覆盖命中、各版本失效、房间切换和错误回退；相同逻辑版本不重复建立稳定数据。
- 线程池分别以 1、2、4、6 个工作线程运行相同固定种子回放，权威状态哈希、事件序列和存档字节完全一致。
- 相同快照和相同 `alpha` 下，各工作线程数产生相同容量、稳定顺序和绘制命令内容；任务队列不得丢失或重复。
- 压力测试覆盖 30 和 96 个怪物、两个主动技能、满地掉落，验证容量推导和预热后 FramePrep/普通呈现路径新增分配为零。
- 批处理测试确认只合并相邻兼容命令，透明/深度顺序不变；着色器失败和容量溢出会完整回退。
- 卡顿注入测试让纯 CPU 帧准备短时超过截止时间，确认应急模式不等待逾期任务、最多外推两帧、稳定 30 帧后退出且权威哈希不变；房间/死亡/材质代际切换不得复用旧帧。稳定 10,000 帧中的误触发率低于 1%，正常路径 CPU active time 不得增加 0.10 ms 以上。主线程或 `EndDrawing()` 强制阻塞必须被记录为不可遮蔽硬卡顿，不能计作插帧成功。
- 生命周期测试覆盖初始化失败、窗口关闭、房间切换和资源卸载，确认所有线程在 raylib/音频销毁前停止。
- Intel 与 NVIDIA 图形路径至少各完成一次启动和渲染冒烟；当前机器分别覆盖垂直同步开启和关闭。

性能报告必须记录提交、构建类型、分辨率、垂直同步、显示刷新率、场景种子、工作线程数、平均 FPS、1% low、P95/P99 与各阶段耗时。功能测试与确定性测试通过不等于性能验收通过。

## 分阶段交付

1. **帧率与输入基础**：应用唯一 240 FPS 上限，保留 60 Hz 权威逻辑，补齐输入边沿和插值测试。
2. **计时与新基线**：加入固定容量分阶段计时，记录当前提交的普通、30 怪物和 96 怪物基线。
3. **稳定缓存**：按版本缓存 HUD、掉落、材质常驻请求及不依赖 `alpha` 的展示数据，并按收益门槛验收。
4. **固定工作线程池**：并行纯 CPU 帧准备，验证 1/2/4/6 线程确定性、串行阈值和生命周期。
5. **卡顿保护**：用已完整发布的命令实现有截止时间、两帧上限和迟滞退出的应急插值帧，验证不可遮蔽卡顿会如实上报。
6. **GPU 提交优化**：在 OpenGL 3.3 下实现相邻材质命令的状态缓存/批处理，保留逐精灵回退。
7. **最终基准与清理**：跑完整测试和真实窗口矩阵，回滚没有达到收益门槛的复杂路径，记录最终数据。

每阶段独立提交、独立验证。后一阶段不能用来掩盖前一阶段功能或性能回归。

## 明确非目标

- 不把完整游戏逻辑、AI、碰撞或伤害提升到 240 Hz。
- 不在本阶段启用 120 Hz 子步；它只保留为有测量证据后的独立方案。
- 不使用光流、AI 造帧或独立渲染线程；应急插值只复用代际兼容的完整命令，并且不能掩盖不可遮蔽硬卡顿。
- 不迁移到 OpenGL 4.3，不使用 Compute Shader 或 SSBO 游戏计算。
- 不把权威玩法、RNG、存档或需要回读的数据迁移到 GPU。
- 不并行化战斗 AI、共享对象池或事件提交。
- 不生成新美术、不增加技能独立素材帧、不重做材质包。
- 不新增无条件全分辨率多通道后处理或突破 256 MiB 材质常驻预算。
- 不以降低画质、减少怪物、缩短特效或改动玩法换取帧率。

## 架构依据

该方案采用商业引擎常见的固定物理/玩法更新与可变呈现分离模式：Unity 区分逐帧更新与固定更新，Godot 将固定物理 tick 配合插值列为常用方法，Unreal 也以可变渲染配合受控物理子步，并明确提示子步的 CPU 成本。项目据此选择 60 Hz 权威逻辑、最高 240 Hz 呈现，而不是全量 240 Hz 模拟。

- Godot Physics Interpolation: <https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html>
- Unreal Engine Physics Sub-Stepping: <https://dev.epicgames.com/documentation/en-us/unreal-engine/physics-sub-stepping-in-unreal-engine>
