# 全游戏结构重构设计（2026-07-27）

## 1. 目标与基线

以提交 `f132f276e5ac8339acb9573146a260193961eeb6` 为唯一基线，对当前
C++17 / raylib 6.0 游戏进行全面但分阶段的行为保持型结构重构。

当前生产代码约 298 个文件、59,192 行。主要热点为：

- `src/platform/raylib/raylib_host.cpp`：4,135 行；
- `src/dungeon/dungeon_session.cpp`：2,466 行；
- `src/dungeon/dungeon_transition.cpp`：2,021 行；
- `src/combat/combat_world.cpp`：1,918 行；
- `src/persistence/checkpoint_codec.cpp`：1,395 行；
- `src/persistence/room_progress_codec.cpp`：1,345 行。

重构目标是恢复清晰职责边界、降低单文件与单函数复杂度、减少真实重复、缩小
编译峰值和后续功能改动的影响面。总行数和单文件行数只用于观察，不作为通过
重构的独立硬指标；不得通过压缩格式、删除必要测试或合并语句制造表面精简。

## 2. 方案决策

评估过三种方式：

1. **分阶段结构重构（采用）**：每次抽离一个现有职责，保持公开行为和数据格式，
   每张任务卡可独立构建、测试、审查和回滚。风险最低，最适合当前已有大量测试
   和架构守卫的代码库。
2. **只处理四个最大文件**：周期较短，但会留下持久化、渲染器和跨模块重复，下一轮
   功能开发仍会把职责重新挤回大文件。
3. **重新设计或重写核心架构**：可能得到更整齐的最终形态，但会同时改变战斗时序、
   RNG、存档和表现层，无法可靠证明行为保持，拒绝采用。

用户已用“重构吧”批准第 1 种推荐方案。

## 3. 全局不变约束

- 不改变任何玩法、数值、按键、动画时序、输入采样时机、帧率策略或镜头行为。
- 不实现尚未完成的正方形百倍房间计划 Task 7 及后续任务，不借重构新增功能。
- 不改变固定步更新顺序、RNG 域、随机调用次数、随机调用顺序或相同种子的结果。
- 不改变 V1-V9 存档字节格式、版本号、迁移规则、双槽事务、刷盘与故障恢复语义。
- 不改变房间、战斗、掉落、药物、深渊、死亡、装备、强化、技能石和 HUD 的外部行为。
- 热路径继续使用固定容量或预分配存储；战斗、房间推进和渲染热路径不得新增堆分配。
- `core` 与领域模块不得包含 raylib 头；`dungeon` 与 `persistence` 不得互相依赖；
  战斗不写文件，存档不推进战斗。
- 不引入 ECS、反射、服务定位器、动态插件系统或没有当前调用者的未来抽象。
- 不删除兼容入口、迁移路径、故障注入点、测试证据或用户已有文件。
- 每次只修改一个职责边界；跨模块接口变化必须让全部调用者在同一任务卡中完成迁移。
- Windows 构建始终串行 `-j1`；监控 MSVC 内存，避免再次触发高提交内存峰值。

## 4. 目标架构与数据流

公开入口和依赖方向保持不变：

```text
app/launcher
    -> platform/raylib + platform/settings
        -> dungeon + persistence
            -> combat + items + skills + passives + progression + abyss
                -> modifiers + core
```

领域模块继续只交换值类型、固定容量快照、命令和事件。`DungeonSession` 仍是地下城
公开门面，`CombatWorld` 仍是战斗公开门面，`DungeonRuntime` 仍拥有会话与保存工作器，
`run_raylib_host()` 仍是平台主入口。重构只把私有实现按职责迁移到更小的翻译单元，
不要求调用者理解新的内部文件布局。

## 5. 子项目拆分与固定顺序

全面重构拆成七个子项目。每个子项目拥有独立实施计划、任务账本、提交和审查门禁；
上一个子项目通过后才开始下一个。

### A. Raylib Host 验收逻辑与主循环

先从 `raylib_host.cpp` 抽离 Stage 10/11/11B/11C/11D/17 的正式验收状态、输入注入、
截图证据和摘要写入逻辑，形成私有 `host_validation_*` 文件。随后把窗口生命周期、
设置预览和逐帧协调拆成小型值类型协作者。`run_raylib_host()` 只保留组装、输入采样、
固定步推进、事件排空、渲染调度与退出码映射。

验收夹具仍由正式游戏目标编译和调用，不移动到测试目标，不改变命令行选项、证据路径、
截图名称或阶段完成条件。

### B. DungeonSession 房间生命周期

按现有成员函数定义拆分为房间构建/人口激活、房间进度与解锁、死亡继续、深渊生命周期、
掉落与药物、保存快照与恢复六类实现文件。`DungeonSession` 的公开头和对象所有权保持不变；
不引入动态多态或跨模块回调框架。

### C. Dungeon 事务请求与提交

将 `dungeon_transition.cpp` 分成出口/下层事务、装备与合成、强化、技能装配、普通/材料/
药物拾取，以及统一保存回执发布。每种事务继续生成原有 `PendingSaveKind`、generation、
verified state 和 rollback/fault 结果；枚举顺序不变。

### D. CombatWorld 模拟职责

把初始化与重置、固定步编排、玩家状态、怪物状态、投射物、危险区域、快照/事件输出迁移到
独立实现文件。已有 `CombatWorld` 数据布局、固定容量池和公开方法不变；不得引入虚函数、
组件注册表或不同的更新顺序。

### E. Persistence 编解码与工作器

按公共 V8 内层格式、V9 房间进度外层、旧版本迁移、结构验证和保存工作器协议拆分文件。
所有黄金字节、CRC、长度、保留字节、尾扩展规则和错误枚举保持逐字节一致。先增加源结构
守卫和黄金输入，再移动实现。

### F. Raylib 渲染器、HUD 与材质加载

拆分 `inventory_renderer`、`hud_renderer`、`material_pack` 和仍然过大的视图数学文件，统一
已有文本测量、纯色选择、裁剪与坐标投影原语。不得修改素材、字体、颜色、布局、绘制顺序、
混合方式或可见像素；本子项目只处理结构。

### G. 全局重复与依赖收尾

只删除经编译器、引用搜索和测试共同证明无调用的私有代码；集中至少有两个真实调用方的
饱和运算、位操作和固定容量遍历。复核 CMake 目标、公开头、include 边界、编译警告和文档。
不创建万能工具库。

## 6. 错误处理与资源策略

- 保留现有 `noexcept`、返回值、fault enum 和事件发布方式；文件拆分不得把故障转换成异常。
- 任何预分配失败、容量溢出、receipt 不匹配或 CRC 错误继续走原有原子失败路径。
- 不在热路径新增字符串、vector 扩容、共享所有权或日志格式化。
- 每次构建前检查并发编译器和可用内存；只允许一个 MSVC 编译进程。
- 若行为黄金值、存档字节、RNG 轨迹、像素证据或零分配检查变化，立即停止该任务卡并定位，
  不修改期望值接受漂移。

## 7. 测试驱动与审查策略

每个子项目采用相同门禁：

1. 记录基线文件规模、符号归属、调用者和目标依赖。
2. 先增加会失败的结构守卫或缺失的特征测试，证明待拆职责和行为边界。
3. 只移动足以让该测试通过的实现，保持测试绿灯后再清理重复。
4. 运行受影响模块单元测试、架构守卫、`git diff --check` 和串行增量构建。
5. 独立审查规格符合性与代码质量；P0/P1/P2 全部关闭后提交。
6. 涉及 Dungeon/Combat/Persistence 的子项目运行相应1000房、确定性、零分配或故障注入测试。
7. 每个子项目末尾运行 Debug 正式门禁；全项目结束时运行 Debug/Release 全量构建与 CTest。
8. 最终启动真实 raylib 游戏，验收移动、攻击、跳跃、上挑、技能、拾取、出口、下层、暂停、
   HUD、存档重启和持续运行；结构重构不能以测试替代可见游戏验收。

## 8. 度量与完成条件

度量目标用于发现拆分失败，不作为通过的唯一条件：

- 最大生产文件从 4,135 行显著下降；任一文件超过约 1,200 行必须在审查报告中解释原因。
- `raylib_host.cpp` 不再包含阶段验收状态机的具体实现。
- `DungeonSession`、`CombatWorld` 和编解码门面的公开调用面不因文件拆分而扩大。
- 生产总行数允许因清晰接口和特征测试小幅变化；必须记录实际增减与原因。
- 所有既有架构守卫继续通过，且不得通过缩小扫描范围来通过。
- Debug/Release 全量门禁、相关压力测试、独立最终审查和真实窗口验收全部通过。
- 最终工作树干净，每个子项目提交可独立回滚，远端分支哈希完成读回校验。

## 9. 明确不做

- 不顺便修改怪物强度、掉率、房间大小、25%出口规则、技能表现或材质包。
- 不顺便优化GPU、插帧、八核并行或240帧策略。
- 不升级raylib、CMake、MSVC或存档版本。
- 不把正式验收代码删除、伪造为测试替身或改成只在开发构建存在。
- 不在本轮合并到 `main`；完成后保留独立分支等待最终合并决策。

## 10. 停止条件

出现以下任一情况时停止自动推进并保留现场：无法证明像素/输入行为等价；存档黄金字节变化；
RNG或更新顺序变化；完整测试出现无法归因的失败；编译再次耗尽系统提交内存；变更必须扩大到
新玩法或未批准的架构；或审查在五轮修复后仍有承重型P0/P1问题。
