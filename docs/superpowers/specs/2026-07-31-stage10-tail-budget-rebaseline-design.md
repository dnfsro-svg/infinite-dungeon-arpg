# Stage 10 稀疏尾图预算重新标定设计

日期：2026-07-31

## 1. 新基线

近身朝向活性修复后，相同 48,914 tick 预算从 486/600 提升为 562/600，剩余
38 只。终态满足：

- 当前无锁，361 次 acquire 全部由 349 次 absent 与 12 次 movement-stall 闭合；
- 12 次 light-lane recovery 全部成功 reacquire；
- `sweep_escape=true`，当前 snapshot 无 resident，但全局仍有 38 个目标；
- 当前 waypoint 下一步会产生非零移动；
- 玩家存活且动作、技能、输入没有阻塞。

因此旧零输入固定点已解除，当前失败是合法稀疏尾图巡航尚未在预算内完成，不再允许
继续改导航、朝向或动作优先级。

## 2. 预算方案

比较三档仿射上限：

| 公式 | 600 怪 | 1125 怪 | 结论 |
| --- | ---: | ---: | --- |
| `12000 + 96N` | 69,600 | 120,000 | 采用 |
| `12000 + 112N` | 79,200 | 138,000 | 当前证据不需要 |
| `12000 + 128N` | 88,800 | 156,000 | 失败资源上限过高 |

采用：

```text
budget(N) = 12000 + 96 * N
```

修复后的总体成本是 `48,914 / 562 = 87.04` tick/kill；斜率 96 提供约 10.3%
人口相关余量，固定 12,000 tick 专门覆盖与人口无关的全房稀疏巡航。600 怪还可获得
20,686 tick 清理 38 只，即约 544 tick/只，是总体成本的 6.25 倍。

合法人口 450/600/1125 对应 55,200/69,600/120,000 tick；容量边界 1152 对应
122,592 tick。先验证 `1 <= N <= kRoomMonsterCapacity`，再用 `uint64_t` 完成加乘并
验证可缩窄为 `uint32_t`。

本公式取代前一设计的 `ceil(N*60000/736)`，但保留同一人口来源、容量检查和失败
诊断合同。

## 3. 超时与资源

将该唯一 transaction fixture 的 CTest `TIMEOUT` 从临时 60 秒调整为 75 秒。
按最新机器实测 `19.4s / 48,914 tick`，1125 怪预算上限约 47.6 秒；清房后固定辅助
循环上限 3,764 tick 约 1.5 秒，合计约 49.1 秒。75 秒保留约 25.9 秒机器/I/O 波动
余量。

超时只限制异常最长时间，不增加正常成功路径耗时。构建与测试继续串行，不启动游戏，
不运行全量 CTest。

## 4. 范围与门禁

- 只修改测试预算 helper 和该测试的单一 CTest timeout。
- 保留已实现的 dense driver、近身朝向活性修复、一次真实完整清房、durable clear
  checkpoint 分叉、领取/放弃/环境证据和全部断言。
- 不改变生产代码、玩法、人口、伤害、奖励、存档、阈值或证据语义。
- 串行目标构建后只运行一次直接门禁；exit 0 后才运行 transaction CTest 与
  `stage10.evidence.no_private_injection`。
- 若 69,600 仍失败，必须保留完整新终态并停止；不得在本卡改成 112N/128N。
