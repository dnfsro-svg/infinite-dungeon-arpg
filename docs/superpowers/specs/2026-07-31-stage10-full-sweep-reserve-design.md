# Stage 10 完整扫图周期储备设计

日期：2026-07-31

## 1. 新证据

`12000 + 96N` 在固定 600 怪房间运行 69,600 tick 后达到 599/600。终态仍为
无锁、无动作阻塞、`sweep_escape=true`，说明人口相关斜率已经基本标定，最后一只的
发现时间取决于当前扫图相位，而不是怪物总数。

验证装备提供 110% 移速，生命献祭不降低地面移速：基速 5.4 u/s 变为 5.94 u/s，
即直线约 0.099 u/tick、对角每轴约 0.070 u/tick。现有 10-waypoint 路径包含五条
约 154.36u 横线、四次约 32.50u 换行和一次约 `(154.36,129.98)` 回绕；计入到达
死区后完整周期约 11,100～11,400 tick。当前终点到 waypoint 4 后覆盖余下完整序列
约需 11,400 tick。

## 2. 最终预算合同

不提高已验证到 599/600 的人口斜率，只增加一个完整扫图周期的固定储备：

```text
budget(N) = 24000 + 96 * N
```

对应：

- 450 怪：67,200 tick；
- 600 怪：81,600 tick；
- 1125 怪：132,000 tick；
- 容量边界 1152：134,592 tick。

继续先验证 `1 <= N <= kRoomMonsterCapacity`，使用 `uint64_t` 加乘并检查缩窄为
`uint32_t`。失败诊断和调用点不变。

该公式取代 `12000 + 96N`。它比把斜率提高到 112N 更符合证据：600 怪时两者都
增加约一个周期，但固定储备不会让尾图成本随高人口继续膨胀。

## 3. 超时与范围

CTest `TIMEOUT` 保持已批准的 75 秒，不再修改 CMake。按最新 0.426ms/tick 估算，
1125 怪预算上限约 56.2 秒，另加辅助流程约 1.6 秒，仍有约 17 秒余量。

只允许把预算 helper 的 base 从 12,000 改为 24,000；不得修改驱动、waypoint、
朝向、动作、生产代码、玩法、人口、奖励、存档、断言或证据护栏。

串行目标构建后直接运行一次；exit 0 后才运行两个精确 CTest。若 81,600 tick 后仍
以无锁扫图和剩余目标失败，停止所有预算增加并转查 residency/waypoint 覆盖。
