# Stage 11-A 死亡与继续闭环设计

## 1. 目标与基线

本任务卡在已验收的 Stage 10 正式深渊房间战斗之上，实现可跨重启、不可重骰的完整单人死亡与继续闭环。玩家死亡后不在原房复活；游戏原子保存死亡回顾和退层目标，显示死亡界面，玩家按 `E` 后进入已经确定的新初始房间。

- 基线提交：`a06eddbdf557b7209146f12ec1a6bc75a1aa75b3`
- 分支：`codex/stage11a-death-continue`
- 工作树：`E:\game\.worktrees\stage11a-death-continue`
- 技术基线：C++17、raylib 6.0、60 Hz 固定逻辑步长、CMake、Ninja、CTest、MSVC 19.44、Windows SDK 10.0.26100.0、Windows x64。
- Stage 10 Debug 基线：43/43 CTest，0 失败。

## 2. 本次范围

本次实现：

- 普通房和深渊房统一的玩家死亡入口。
- 死亡时停止战斗模拟与玩法输入。
- 最近 5 秒承伤统计、最后一击和死亡时防御快照。
- 两阶段原子死亡事务：`death_retreat` 与 `death_continue`。
- 死亡后退回上一层；第 1 层死亡仍进入新的第 1 层初始房。
- 死亡回顾跨重启恢复。
- 检查点 V6、V5 迁移和双槽故障恢复。
- raylib 死亡覆盖层、输入限制、真实窗口截图验收。
- 确定性、固定容量、零热路径分配和长程压力验证。

本次不实现：

- 设置菜单或按键重绑定。
- 物品过滤器。
- 完整 HUD 重制。
- macOS 构建与验证。
- 全游戏性能优化。
- 首领、层主、召唤、光环。
- 新装备、新装备词缀、新怪物词条或新深渊奖励。
- 城镇、安全营地、角色选择或多存档角色界面。

## 3. 玩家可观察规则

### 3.1 死亡惩罚

第 2 层及以上死亡时，目标深度为当前深度减 1。第 1 层死亡时，目标深度仍为 1。继续后的目标房固定满足：

- `floor_room_index = 0`；
- `EntrySide = initial`；
- 四种元素偏向全部为 0；
- `TransitionKind = death_retreat`；
- 房间不是深渊；
- 普通洞口仍由目标房种子按现有固定概率决定。

死亡不扣除角色等级、当前经验、已获得或未分配技能点、星盘分配、装备和背包。已经原子提交的永久收益保留。当前房间进度、地面装备、尚未提交的房间经验与奖励、当前层元素偏向和当前深渊机会永久丢失。

### 3.2 两阶段继续

玩家生命归零后：

1. 立即冻结战斗。
2. 构造并保存 `death_retreat`，一次性确定死亡摘要和退层目标。
3. 提交成功后发布 `pending_continue`，显示死亡回顾。
4. 玩家按 `E` 构造 `death_continue`。
5. `death_continue` 提交成功后销毁死亡房，进入已保存目标。

玩家在死亡界面强退时，重启必须恢复同一份死亡回顾和同一目标房。不得直接跳过死亡状态，不得重骰房间种子、生态或洞口。

### 3.3 深渊死亡

深渊房死亡与普通死亡使用同一退层流程，同时在同一个 `death_retreat` 事务中：

- 将深渊挑战标记为失败；
- 销毁当前深渊房与地面奖励；
- 写入合法的 `LastAbyssResolution = failed`；
- 保存死亡回顾中的“死亡房为深渊”；
- 保存退层后的普通初始房目标。

Stage 10 的“深渊死亡后留在原房并转普通房”是阶段性验收行为；Stage 11-A 正式规则取代该行为。

## 4. 核心状态与模块边界

### 4.1 状态模型

检查点新增 `DeathCheckpoint`，生命周期只有：

- `none`：没有待处理死亡；其余死亡字段必须为规范零值。
- `pending_continue`：死亡已原子提交，等待玩家继续。

`DeathCheckpoint` 保存：

- 死亡所在深度、层内房间编号、生态和是否深渊；
- 稳定致死来源标识、伤害类型、最后一击原始伤害；
- 最后一击护盾损失、生命损失和最终承伤；
- 最近 5 秒物理、火、水、电、混沌实际承伤汇总；
- 死亡时最大/当前生命、最大/当前护盾、护甲值与减伤率、闪避值与闪避率、四元素减伤率与上限；
- 完整目标房间描述；
- 死亡数据版本。

运行状态另保存单调递增的 `death_sequence`。它只在 `death_retreat` 成功提交时增长，不能在准备、失败或重试时提前增长。

### 4.2 模块职责

- `combat`：记录固定容量承伤历史，判定玩家死亡，生成不含地下城语义的死亡战斗快照。不得读取存档、深度、房间或 raylib。
- `dungeon`：把战斗死亡快照与房间/深渊状态组合成 `DeathCheckpoint`，生成退层目标，编排两阶段事务，控制房间生命周期。
- `persistence`：编码、解码、CRC、V5→V6 迁移和双槽恢复。除稳定 checkpoint 类型外不得依赖 dungeon 实现。
- `platform/raylib`：只读取公开快照，渲染死亡覆盖层并把 `E` 转换为继续请求。不得直接写稳定状态或构造目标房。
- `items`、`progression`、`passives`、`modifiers`：不新增死亡控制流程；它们的稳定状态由 dungeon 原样保留。

## 5. 承伤历史与致死来源

### 5.1 300 tick 固定滚动窗口

Combat 使用固定 300 桶滚动窗口，对应 60 Hz 下最近 5 秒。每个桶保存五类实际承伤饱和值：物理、火、水、电、混沌。

- 每个逻辑 tick 开始时推进一个桶并清零被复用位置。
- 同 tick 多次命中按类型累加。
- 闪避成功不计入承伤。
- 护盾吸收和生命损失都属于实际承伤；最后一击额外拆分二者。
- 所有累计使用饱和整数，禁止无符号回绕。
- Update 热路径不得进行堆分配。
- 渲染帧率不得改变窗口内容或淘汰时机。

死亡发生时，Combat 冻结一个 `CombatDeathSnapshot`。之后怪物、投射物、危险区、效果计时和玩家状态均不再推进，直到 DungeonSession 发布新的房间。

同一固定 tick 内按既有确定性更新顺序处理伤害；第一笔把生命降至 0 的伤害是最后一击，之后的伤害不再结算。如果玩家与最后一个怪物在同一 tick 死亡，玩家死亡优先于清房和房间奖励，符合“死亡丢失当前房进度”的规则。

### 5.2 稳定来源

致死来源由稳定枚举和数值 ID 组成，不保存界面字符串：

- 来源类别：怪物攻击、投射物、地面危险、怪物词条、深渊环境、未知；
- 怪物原型 ID；
- 攻击、危险、词条或深渊规则 ID；
- 伤害类型。

来源不能可靠归属时必须使用显式 `unknown`，不得伪造成默认怪物。raylib 通过现有目录把 ID 映射为显示文本。

## 6. 确定性退层目标

退层目标使用独立命名随机域 `death_retreat`。输入固定包含：

- 当前稳定房间种子；
- 当前提交代数；
- 下一 `death_sequence`；
- 目标深度；
- 固定随机域常量。

输出必须为非零目标房间种子；零结果使用固定非零重映射，不允许重新抽取。Dungeon 在准备 `death_retreat` 时由该种子生成完整目标描述并写入下一稳定状态。receipt 重试必须逐字段相同。

`death_sequence` 或提交代数已经达到最大值时，Session 在构造 pending save 前进入明确的 overflow fault；不得回绕、夹紧或复用旧序号。

目标描述使用现有普通房生成规则，但强制初始入口、层内房间编号 0、零偏向和非深渊。洞口与生态仍从目标种子的各自独立随机域生成。死亡流程不得消费普通门、洞口、深渊、怪物、词缀或掉落随机流。

## 7. 原子事务与生命周期

### 7.1 `death_retreat`

准备条件：

- Session 非 faulted；
- 没有其他 pending save；
- Combat 已产生且只产生一次玩家死亡快照；
- 当前房仍处于战斗状态；
- 没有已发布的死亡状态。

现有非死亡 pending save 会冻结 Combat，因此不能在其未决期间产生新的死亡。如果同一平台帧同时带来死亡事件和背包、拾取、星盘或导航请求，DungeonRuntime 必须先处理固定逻辑 tick 的死亡结果，拒绝其余玩法请求，再构造唯一 `death_retreat`。

下一稳定状态必须：

- 保留已提交的角色、物品、星盘和永久进度；
- 清空地面池与当前房未提交奖励；
- 递增 `death_sequence`；
- 写入 `pending_continue` 与完整目标；
- 普通死亡不修改 `LastAbyssResolution`；
- 深渊死亡原子发布 failed lifecycle 与 failed resolution。

进入 `pending_continue` 时，稳定 `current_room` 仅作为已销毁死亡房的历史锚点，不再构建 Combat；其 `is_abyss` 必须规范化为 false。死亡房原本是否为深渊只从 `DeathCheckpoint` 读取，避免与 Stage 10 的 failed checkpoint 约束冲突。

只有 verified committed receipt 且旧状态、下一状态、kind、代数完全匹配时，Session 才发布死亡回顾。`not_committed` 丢弃 pending save，但保持战斗冻结，并允许确定性重试。`indeterminate` 或任何 receipt 不匹配进入 faulted。

### 7.2 `death_continue`

准备条件：

- 稳定状态为 `pending_continue`；
- 没有其他 pending save；
- 当前没有可运行 Combat；
- 目标描述通过确定性和结构校验。

下一稳定状态把目标描述发布为当前房，清空 DeathCheckpoint，保留已递增的 `death_sequence`，然后按普通初始房流程构建 Combat。只有 verified committed receipt 才能发布新房。

`not_committed` 保持死亡回顾，可再次按 `E`。`indeterminate` 或 receipt 不匹配进入 faulted。继续请求不得再次增加死亡序号。

## 8. V6 持久化与校验

V6 在 V5 稳定字段之后追加 `death_sequence` 和 `DeathCheckpoint`。V5 迁移规则固定为：

- `death_sequence = 0`；
- `DeathCheckpoint.lifecycle = none`；
- 其他 V5 角色、进度、星盘、物品、房间、深渊和摘要字段逐字节保持语义。

V6 解码与 Session 构造共同防御以下非法状态：

- `none` 带非零死亡载荷；
- 非法生命周期、来源、伤害类型，或结构上不允许的零/非零 ID 组合；
- 最后一击分项与最终承伤矛盾；
- 最近 5 秒分项溢出或不规范；
- `pending_continue` 仍带地面物品；
- 目标深度不是 `max(1, death_depth - 1)`；
- 目标层内房间编号、入口、偏向、transition 或深渊标记错误；
- 目标描述与确定性重新生成不一致；
- 普通死亡伪造深渊失败；
- 深渊死亡缺少合法 failed lifecycle 或 failed resolution；
- 截断、尾随字节、CRC、版本和双槽代数错误。

Codec 只做结构与稳定字段关系校验。需要 DungeonRules 的重新生成一致性由 DungeonSession 构造时防御性完成。
Combat、怪物词条、危险区和深渊目录中是否真实存在相应 ID，也由拥有这些目录的运行时层校验；Persistence 不依赖目录实现。

## 9. 死亡覆盖层与输入

死亡回顾在真实游戏画面上绘制全屏覆盖层，显示：

- 死亡所在深度、房间编号、生态和深渊标记；
- 致死来源和伤害类型；
- 最后一击原始伤害、护盾损失、生命损失、最终承伤；
- 最近 5 秒五类承伤统计；
- 死亡时生命、护盾、护甲减伤、闪避率和四元素减伤；
- `第 N 层 → 第 M 层`；
- `E 继续`。

死亡检测后、`death_retreat` 提交前显示“正在记录死亡”，不得显示可继续提示。`pending_continue` 只接受：

- `E`：请求继续；
- `F12` 或 `V`：截图；
- `F1`：调试信息；
- `Esc`：退出游戏。

WASD、J、K、L、R、I、P、门和洞交互全部禁用。`death_continue` 保存失败时保持死亡回顾并显示保存失败；再次按 `E` 重试相同下一状态。

## 10. 测试与正式验收

### 10.1 无窗口测试

- Combat：五类承伤、同 tick 累加、闪避排除、护盾/生命拆分、300 tick 精确淘汰、饱和、冻结、零分配。
- Dungeon：普通死亡、深渊死亡、深度 1、深层退层、地面池清空、永久状态保留、两阶段事务、重复请求、输入门禁。
- Persistence：V6 往返、V5 迁移、所有非法组合、截断/尾随/CRC、双槽旧/新 winner。
- Receipt：两种事务的 committed、not_committed、indeterminate，以及 kind、代数、旧状态、下一状态不匹配。
- Platform：快照映射、死亡覆盖层布局数据、允许/禁止输入矩阵。
- Architecture：核心模块继续禁止 raylib；combat 禁止 dungeon/persistence；persistence 只依赖 checkpoint 稳定类型。

### 10.2 压力与确定性

连续执行 1000 次死亡与继续；覆盖第 1 层夹紧、深层退层、普通/深渊死亡，并定期 V6 encode/decode 和重建 Session。两个相同根状态必须得到完全相同的死亡摘要、目标种子、目标描述和最终 hash。

压力测试同时验证：

- Combat 伤害记录和死亡 tick 零堆分配；
- 固定池饱和时死亡事务仍可构造，地面内容不会泄漏到死亡存档；
- 1000 次循环无持续内存增长；
- 不消费其他命名随机流。

### 10.3 正式 raylib 路径

正式窗口必须通过生产输入和生产存档路径完成：

1. 普通房死亡并显示完整回顾；
2. 在死亡界面退出，重启后显示相同回顾；
3. 按 `E` 后从深层退回上一层新初始房；
4. 第 1 层死亡后进入新的第 1 层初始房；
5. 深渊死亡写入 failed resolution 并退层。

截图只能在真实 `EndDrawing` 后通过唯一正式 helper 生成。证据守卫必须拒绝私有注入、预绘制截图、伪造死亡快照或直接修改 Session 内部状态。
