# Stage 2 最小房间主循环设计

## 1. 目标

在 Stage 1 战斗实验室基础上，交付可见、可操作、可无窗口验证的最小单向房间主循环：进入房间后锁门，使用现有三个被动木桩作为临时战斗目标，全部击败后同时开启上、下、左、右四个一次性出口；玩家走入一个出口后立即提交选择、永久销毁旧房，并在下一固定 tick 生成新房。

Stage 2 只验证房间生命周期、单房常驻、出口提交、确定性房间序列和长期内存稳定性。元素偏向、下坠洞、深渊、正式怪物 AI、刷怪导演、奖励、掉落与存档属于后续里程碑。

## 2. 已确认范围

### 2.1 清房目标

- 每个活动房间固定生成现有轻型、普通和重甲木桩各一个。
- 三个木桩 HP 全部归零后，本房清理结果永久成立。
- Stage 2 房间中的木桩死亡后不自动复活。
- 不新增追击、攻击、寻路、投射物或玩家受伤规则。

### 2.2 出口交互

- 房间始终显示上、下、左、右四扇门。
- 清房前四门关闭，玩家不能离开。
- 清房后四门同时开放。
- 玩家走入门洞并继续向房间外移动时提交选择，不增加交互键。
- 未选择的三扇门不生成、不缓存也不保存候选房。
- 下一房的反方向门不是返回门；它在下一次清房后仍是一个全新的一次性出口。

### 2.3 明确排除

- 火、水、电、混沌偏向及任何方向权重。
- 普通洞口、无限深度、深渊房和对应随机投掷。
- 正式怪物、敌人 AI、敌人攻击、玩家生命和玩家受击。
- 房间奖励、经验、装备、掉落、背包和自动收取。
- 存档、崩溃恢复、原子持久化和防重骰协议。
- 双向连接、返回旧房、回环、房间坐标网络和迷宫小地图。
- 同时加载、更新或渲染多个房间。

## 3. 模块与依赖边界

新增纯 C++ 静态库 `arpg_dungeon`，放在 `src/dungeon/`。依赖方向固定为：

```text
arpg_core <- arpg_combat <- arpg_dungeon <- arpg_raylib <- arpg_game
```

- `arpg_dungeon` 可以使用 `arpg_core` 的确定性随机和有界队列，也可以组合 `CombatWorld`。
- `arpg_core` 与 `arpg_combat` 不得反向包含或链接 `arpg_dungeon`。
- `arpg_dungeon` 不得包含、链接或通过编译选项间接依赖 raylib。
- raylib Host 只通过 `DungeonSession` 的公开输入、快照和事件接口驱动游戏。
- renderer 不决定清房、开门、出口提交或房间种子。

## 4. 主要类型与职责

### 4.1 DungeonSession

`DungeonSession` 是 Stage 2 的规则入口，固定拥有：

- 根种子。
- 全局固定 tick 计数。
- 当前房间序号与种子。
- 当前进入侧和上次提交方向。
- 房间生命周期状态。
- `std::optional<CombatWorld>`：唯一活动战斗房间。
- 固定容量地下城事件队列。
- 诊断与错误状态。

它提供：

- 离散战斗动作入队。
- 每固定 tick 的方向输入与规则推进。
- 当前房间重置。
- 只读 `DungeonSnapshot`。
- 地下城事件与战斗事件的有界弹出接口。

Host 不取得可变 `CombatWorld&`，防止绕过房间状态机。

### 4.2 DungeonSnapshot

快照至少包含：

- session tick。
- 房间序号与房间种子。
- 房间生命周期状态。
- 是否存在活动房间。
- 四门是否开放。
- 剩余目标数。
- 当前进入侧与上次出口方向。
- 可选的 `CombatSnapshot`。
- 地下城事件溢出、非法出口请求与房间序号溢出诊断。

快照为固定大小值类型，不持有指针、动态容器或旧房间引用。

### 4.3 CombatLabConfig 扩展

为保持 Stage 1 行为并支持 Stage 2，配置增加：

- 初始玩家朝向，默认向右。
- 木桩死亡后是否自动复活，默认 `true`。

Stage 1 默认配置保持原来的 90 tick 自动复活。Stage 2 生成房间时将自动复活设为 `false`。

## 5. 生命周期与数据流

状态流固定为：

```text
Locked -> Combat -> Cleared -> AwaitingExit -> Transitioning -> Locked(new room)
```

### 5.1 Locked

- 新房已经构造，四门关闭。
- 构造后的首个固定 tick 只将状态推进到 `Combat`，不提前执行战斗更新。
- 发出进入房间与开始战斗事件。

### 5.2 Combat

- 战斗动作和方向输入转发给当前 `CombatWorld`。
- 每 tick 更新后检查三个木桩 HP。
- 三者第一次全部为零时进入 `Cleared`，结果不可逆，发出一次清房事件。

### 5.3 Cleared

- 四门立即标记为开放。
- 木桩保持死亡，不再复活。
- 发出一次开门事件。
- 下一固定 tick 进入 `AwaitingExit`。

### 5.4 AwaitingExit

- 当前 `CombatWorld` 继续处理玩家移动，方便玩家走到门口。
- 出口检测在本 tick 移动完成后执行。
- 只有处于对应门洞范围、位于房间边界且方向输入继续向外时才能提交。
- 首个有效出口提交成功；同 tick 或后续请求全部拒绝。

### 5.5 Transitioning

出口提交时按顺序执行：

1. 记录出口方向。
2. 检查房间序号是否可安全增加。
3. 根据当前房间种子、下一房间序号与方向派生下一房种子。
4. 销毁 `std::optional<CombatWorld>` 中的旧实例。
5. 发出出口提交与房间销毁事件。
6. 进入 `Transitioning`；快照中 `has_active_room == false`。

下一固定 tick 才原地构造新 `CombatWorld`、房间序号加一并进入 `Locked`。Transitioning 期间不保存或绘制旧演员快照。

## 6. 门洞与出生模板

房间继续使用 `X [-8.0, 8.0]`、`Y [-3.5, 3.5]`、地面 `Z = 0.0`。

### 6.1 门洞判定

- 左门：`X == -8.0`、`abs(Y) <= 0.90`、输入继续向左。
- 右门：`X == 8.0`、`abs(Y) <= 0.90`、输入继续向右。
- 上门：`Y == -3.5`、`abs(X) <= 1.50`、输入继续向上。
- 下门：`Y == 3.5`、`abs(X) <= 1.50`、输入继续向下。

边界比较使用与 `CombatWorld` 房间钳制一致的确定值，不依赖渲染坐标或插值位置。

### 6.2 初始房间

- 玩家出生在 `{0.0, 0.0, 0.0}`，面向右。
- 三个木桩沿用 Stage 1 出生位置。

### 6.3 后续房间

玩家从所选出口对应的新房入口侧生成：

- 选择左门：新房从右侧进入，玩家 `{6.50, 0.0, 0.0}`，面向左；木桩在左半区镜像排列。
- 选择右门：新房从左侧进入，玩家 `{-6.50, 0.0, 0.0}`，面向右；木桩沿用右半区排列。
- 选择上门：新房从下侧进入，玩家 `{0.0, 2.75, 0.0}`；木桩在上半区横向排列。
- 选择下门：新房从上侧进入，玩家 `{0.0, -2.75, 0.0}`；木桩在下半区横向排列。

上下入口的三木桩横向排列，使玩家到达对应 Y 区域后仍使用现有左右朝向攻击。出生模板集中在 dungeon 房间生成代码中，不散落到 Host 或 renderer。

## 7. 确定性种子与房间生成

- `RaylibHostConfig::root_seed` 正式传入 `DungeonSession`。
- 初始房间种子由根种子和房间序号 `0` 派生。
- 只有出口正式提交后才派生下一房种子。
- 派生输入固定为当前房间种子、下一房间序号和稳定方向 ID。
- 方向 ID 固定为 `up=0`、`down=1`、`left=2`、`right=3`。
- 未选择出口不派生种子，不消耗随机流。
- Stage 2 的内容模板固定，但仍保存并显示房间种子，为 Stage 3 的独立生态、洞口与深渊随机流提供稳定入口。
- 相同根种子和相同出口序列必须产生完全相同的房间种子、出生模板、快照摘要与事件摘要。

## 8. 重置、事件与错误处理

### 8.1 当前房间重置

`R` 调用 `DungeonSession::reset_current_room()`：

- 使用相同房间序号、房间种子和进入侧重建当前房。
- 状态回到 `Locked`，四门关闭。
- 不增加房间序号，不生成新种子，也不改变当前房间种子与进入侧。
- 先清空旧战斗输入、战斗事件、Hit Stop、地下城瞬时事件和表现层瞬时反馈，再发出恰好一次 `room_reset`。

### 8.2 地下城事件

事件种类固定包含：

- `room_entered`
- `combat_started`
- `room_cleared`
- `exits_opened`
- `exit_committed`
- `room_destroyed`
- `room_reset`
- `faulted`

事件队列容量为 32。事件至少携带 session tick、房间序号、房间种子和可选出口方向。规则状态是事实来源；事件溢出不能回滚已经完成的状态转换，但必须累计诊断计数，并在 Debug 与测试中失败。

### 8.3 非法操作

- 清房前触碰门：忽略，不改变状态。
- 不在门洞范围内向外移动：忽略。
- `AwaitingExit` 以外的出口请求：拒绝并累计诊断。
- 出口已经提交：后续提交拒绝，不重复派生种子。
- 房间序号为 `uint64_t` 最大值：生命周期保持 `AwaitingExit`，设置 `room_index_overflow` 错误标志并发出一次 `faulted` 事件；保留当前已清房快照，拒绝销毁和继续切换，不允许静默回绕。

## 9. raylib Host 与表现

- Host 持有 `DungeonSession`，不再直接持有 `CombatWorld`。
- J/K/L 动作和 WASD 方向输入通过 session 转发。
- CombatEvent 继续驱动现有火花、残影、音效与震屏。
- DungeonEvent 驱动门状态、切换淡出和瞬时反馈清理。
- 插值只在前后快照属于同一个活动房间时执行；跨房间或无活动房间时不插值旧演员。

四门视觉：

- Locked/Combat：暗灰门框与红色封锁屏障。
- Cleared/AwaitingExit：中性青白门框、无屏障、显示方向箭头。
- 不使用火、水、电、混沌颜色或标签。
- Transitioning：短暂淡出，不绘制旧演员或旧房快照。

HUD 增加房间序号、生命周期状态、剩余目标数、门状态、上次出口；F1 调试模式额外显示房间种子。窗口标题改为 `Infinite Dungeon - Stage 2 Room Loop`。原有攻击反馈、演员排序、F12 截图和退出行为保持不变。

## 10. 固定容量与性能

- 同时最多一个活动 `CombatWorld`。
- 不保存房间历史、候选房、旧 CombatSnapshot 或房间坐标图。
- DungeonSnapshot、DungeonEvent 和房间描述均为固定大小值类型。
- 地下城事件使用现有固定容量有界队列。
- 房间切换通过 `std::optional::reset/emplace` 原地销毁与构造，不进行实体容器扩容。
- 固定 tick、出口提交和房间切换热路径不得持续进行堆分配。

## 11. 无窗口测试

新增 `dungeon.units`，至少覆盖：

1. 初始房间为 Locked，首 tick 进入 Combat，四门关闭。
2. 清房前四边界与四门洞均不能触发切换。
3. 三木桩全部死亡后只产生一次清房和开门事件。
4. 木桩在清房后不自动复活。
5. 上、下、左、右门洞范围与向外输入判定。
6. 出口只提交一次，旧房立即销毁，Transitioning 无活动房间。
7. 下一 tick 构造唯一新房，序号加一，种子按提交方向确定。
8. 四种进入侧对应的玩家、朝向和木桩出生模板。
9. 新房反方向门不返回旧房。
10. R 使用相同种子重建当前房且不增加序号。
11. 相同根种子和方向序列的两个 session 快照与事件完全一致。
12. 1000 房连续推进中只有一个活动房间，旧房不再更新。
13. 1000 房循环无持续堆分配、无事件溢出、无序号回绕。
14. 房间序号上限和非法提交进入明确诊断路径。

架构守卫新增 `architecture.dungeon_no_raylib`，并验证 combat 不依赖 dungeon。现有 core、combat、platform 测试必须继续通过。

1000 房压力测试只使用公开生产接口和真实 CombatWorld 规则，不增加强制清房或测试专用生产 API。

## 12. 可见验收

- 启动后第一房显示玩家、三个木桩和四扇关闭的门。
- 击败全部木桩后四扇门同时开放。
- 玩家可实际走入任意方向门，不需要额外按键。
- 提交后出现短暂切换，新房从正确入口侧生成。
- 旧房、旧演员、旧火花、旧伤害数字和旧音频请求不再出现。
- 房间编号每次只增加一；R 只重置当前房。
- 连续手动通过至少 20 个房间无残留演员或反馈。
- 1000 房无窗口压力测试通过。
- Debug、Release、core-only 和全部 CTest 通过；Release 继续静态链接 raylib 6.0，无 raylib DLL。
