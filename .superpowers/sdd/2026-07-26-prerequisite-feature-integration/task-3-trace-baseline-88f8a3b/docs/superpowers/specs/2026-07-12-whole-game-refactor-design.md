# 全游戏行为保持型重构设计

## 1. 目标

在不改变游戏玩法与外部行为的前提下，对当前全部生产代码进行分阶段重构和精简。重构以降低复杂度、拆分职责、删除真实重复和改善依赖边界为目标，同时希望减少无必要代码，但不设置代码行数硬指标，也不通过压缩格式或删除必要说明制造表面精简。

本工作在 Stage 6 完成后进行，属于独立重构里程碑。完成后停止，不进入 Stage 7 星盘开发。

## 2. 不变约束

以下行为必须保持：

- WASD、J、K、L、E、F1、F12、R 与 Esc 的现有含义。
- 战斗数值、攻击时序、输入缓存、浮空、击退、护盾和 Modifier/Effect 结果。
- 固定时间步、显式随机种子和相同种子下的确定性结果。
- 房间生命周期、四向元素偏向、洞口、深渊占位、原子房间切换和奖励结算规则。
- 角色等级、经验、技能点和 Stage 5 进度规则。
- 当前存档版本、旧版迁移、双槽事务保存和故障恢复行为。
- HUD 与 F1 诊断信息的语义。
- 热路径固定容量、零堆分配和核心模块不依赖 raylib 的边界。

允许调整内部类型、私有接口、函数归属和文件布局。公开接口仅在全部调用方同步迁移且特征测试证明行为不变时调整。

## 3. 明确不做

- 不实现 Stage 7 星盘或任何后续玩法。
- 不调整平衡数值、按键、动画节奏或随机权重。
- 不提升存档版本，不删除旧存档兼容。
- 不引入新依赖、大型框架、通用 ECS 或反射系统。
- 不创建没有当前调用者的未来抽象。
- 不以合并语句、删除必要注释或降低可读性换取行数下降。

## 4. 总体策略

重构使用基于 Stage 6 的独立 Git 工作树。实施按模块拆成六张连续任务卡，每张任务卡保持可构建、可测试、可独立提交。顺序固定为：

1. CombatWorld 与怪物 AI。
2. DungeonSession 与刷怪导演。
3. raylib 渲染与主循环。
4. 存档、事务保存与编解码。
5. Core、Progression 与 Modifier 公共模块。
6. 全局命名、重复代码和依赖边界收尾。

不得跨任务卡并行修改同一核心文件。每张任务卡完成并验证后才进入下一张。

## 5. Combat 重构

### 5.1 CombatWorld

将现有实现按职责整理为：

- 战斗状态编排与固定步更新。
- 玩家攻击、命中和伤害结算。
- 怪物模拟与效果拥有者管理。
- 快照和事件输出。

公开的 `CombatWorld` 仍是调用入口。内部可通过小型私有辅助类型和分文件实现降低主文件复杂度，不引入动态多态。

### 5.2 怪物 AI

将怪物逻辑按近战、远程/支援和特殊机制分离。统一以下重复原语：

- 有界计时器递减。
- 状态进入与结束。
- 合法目标筛选。
- 方向和距离计算。
- Effect 命令提交与护盾同步。

不同怪物的可读职责和时序保持不变。不得把所有怪物重新塞入一个通用条件解释器。

### 5.3 热路径

对象池、事件队列、EffectSet 和临时集合继续使用固定容量。战斗更新、命中与渲染路径不得增加堆分配。

## 6. Dungeon 重构

将 `DungeonSession` 的职责整理为：

- 房间生命周期推进。
- 战斗会话拥有与事件转发。
- 奖励结算。
- 出口或洞口的事务式提交。
- 快照组装。

重复的房间状态检查集中为有语义的谓词。刷怪导演拆分预算计算、候选过滤和确定性选择，但必须保证相同种子、深度、生态与预算产生相同结果。

房间切换的持久化顺序不得改变，旧房间仍在提交后永久销毁。

## 7. raylib 表现层重构

将大型渲染实现按以下职责拆分：

- 房间与出口绘制。
- 玩家、怪物、投射物和危险区域绘制。
- 战斗反馈与特效绘制。
- HUD、提示和 F1 调试层。

主循环只保留输入采样、固定步更新、事件排空和渲染调度。重复的文本行布局、颜色选择、坐标投影和状态判断提取为局部、明确的辅助函数。

不得改变现有画面含义、控制响应或输入采样时机。

## 8. Persistence 重构

将持久化代码分成：

- 存档路径与槽位选择。
- 编码、解码和版本迁移。
- 临时文件、刷盘、替换与回滚组成的事务保存。
- 双槽检查、恢复和错误映射。

合并重复的文件状态检查和错误转换，但保留当前故障注入点及其测试能力。现有存档字节布局和版本不变。

## 9. 公共模块重构

Core、Progression 与 Modifier 只处理已出现的重复：固定容量遍历、饱和运算、边界验证和稳定排序。公共辅助必须至少有两个真实调用方，或能显著消除一个高风险算法的重复。

禁止创建万能工具类、全局服务定位器或与当前功能无关的扩展点。

## 10. 全局收尾

- 删除确认无调用方的私有接口和重复常量。
- 修正不再准确的兼容注释和命名。
- 检查所有模块 CMake 依赖与架构扫描。
- 保留仍被运行路径、测试或存档迁移使用的兼容接口。
- 记录重构前后生产代码行数、最大文件和模块依赖，仅作为结果说明。

## 11. 实施流程

每张任务卡采用同一流程：

1. 记录修改前模块规模与依赖。
2. 运行模块现有测试建立基线。
3. 对高风险但覆盖不足的行为增加特征测试。
4. 每次只迁移一个职责边界。
5. 运行模块测试和架构测试。
6. 检查差异，确认没有混入玩法变化。
7. 独立提交后进入下一任务卡。

若随机结果、战斗数值或存档字节变化，立即停止并定位来源。不得仅修改测试期望以接受行为漂移。若一次拆分增加重复或接口复杂度，则放弃该局部方案，重新设计边界。

## 12. 验收

每张任务卡至少通过对应模块测试和全部架构测试。最终验收必须包括：

- Debug 全量构建和 CTest。
- Release 全量构建和 CTest。
- 1000 房压力测试及持续内存稳定性检查。
- 旧存档读取、迁移、事务恢复和故障注入测试。
- Modifier/Effect、战斗与随机确定性测试。
- 真实 raylib 窗口验收 WASD、J、K、L、E、F1、房间切换和持续运行。
- 重构前后文件规模、依赖和主要重复热点对比。

全部通过后停在独立重构分支，等待用户验收，不进入 Stage 7。
