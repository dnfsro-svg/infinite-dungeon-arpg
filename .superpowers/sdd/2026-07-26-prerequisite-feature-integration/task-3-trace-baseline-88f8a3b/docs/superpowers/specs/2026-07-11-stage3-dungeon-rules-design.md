# Stage 3 地下城正式规则设计

日期：2026-07-11

状态：已完成分段确认，等待书面规格复核

里程碑分支：milestone/m03-dungeon-rules

## 1. 目标

在 Stage 2 最小单向房间循环上交付可见、可持久化、可确定性复现的地下城正式规则：

- 上、下、左、右分别代表火、水、电、混沌路线。
- 路线选择在当前层累计元素偏向，并影响下一实际房间的主生态。
- 每个实际新房独立判定 10% 普通下坠洞与固定 1% 深渊。
- 下坠进入下一深度，重置本层房间序号与全部元素偏向。
- 出口或洞口选择先持久化，再销毁旧房，保证崩溃不能返回旧房或重骰。
- raylib 中提供元素门、生态色调、深渊主题、洞口交互、存档提示与诊断信息。
- 连续通过 1000 个房间时，状态确定、容量有界且无持续内存增长。

本阶段继续使用 Stage 2 的三个测试目标。正式怪物、奖励、掉落和构筑系统不属于本里程碑。

## 2. 已确认参数

### 2.1 元素路线

| 出口 | 元素 | 稳定 ID |
| --- | --- | --- |
| 上 | 火 | 0 |
| 下 | 水 | 1 |
| 左 | 电 | 2 |
| 右 | 混沌 | 3 |

四元素初始基础权重均为 100。每次选择元素门时，对应偏向增加 1 点；每点增加 25 权重。初版公式为：

元素权重 = 100 + 偏向点数 × 25

该数值是 Stage 3 的已确认验收默认值，必须集中在数据配置中。未来调整需要独立任务卡，不得散落硬编码。

### 2.2 房间随机

- 普通下坠洞：每个实际新房独立 10%，无保底。
- 深渊：每个实际新房独立 1%，无保底。
- 洞口与深渊允许共存。
- 元素生态、洞口、深渊使用三个独立随机流。
- 深度、偏向、角色状态和历史未命中次数不得改变洞口或深渊概率。
- 初始房间、元素门后的房间、下坠后的新层首房都执行一次完整判定。

### 2.3 存档恢复精度

Stage 3 保存地下城稳定状态，不保存战斗中位置、生命值、输入缓存、特效或音频状态。战斗中重载会从同一房间的初始战斗模板重新开始，但房间种子、生态、洞口和深渊结果保持不变。

## 3. 明确排除

- 正式怪物 AI、怪物攻击、玩家生命和死亡流程。
- 刷怪导演、四元素怪物池与怪物词条。
- 房间奖励、经验、装备、掉落、背包和自动收取。
- 深渊专属怪物、奖励、材料、装备和首领。
- 多存档槽选择界面、角色选择、标题菜单和新游戏菜单。
- 完整战斗快照与逐帧战斗恢复。
- 云存档、网络同步、多人游戏和服务器。
- 双向房间、返回旧房、回环、迷宫坐标网络和小地图。
- 同时加载或模拟多个房间。

## 4. 架构与依赖边界

### 4.1 dungeon 规则层

dungeon 保持纯 C++ 且不依赖 raylib，负责：

- 房间、深度和本层房间序号。
- 四元素偏向与主生态抽取。
- 洞口、深渊及独立随机流。
- 门与洞口请求。
- 待持久化切换事务。
- 保存成功或失败后的生命周期推进。

DungeonSession 不直接访问文件系统。它只产生待保存的稳定检查点，并接收保存成功或失败的明确结果。

### 4.2 persistence 持久化层

新增独立 arpg_persistence 目标，仅依赖标准库和 dungeon 的稳定检查点数据，不依赖 raylib。它负责：

- 固定版本的二进制编码与解码。
- CRC32 完整性校验。
- 双槽选择、写入、回读和恢复。
- 损坏文件归档。
- 可注入目录和故障点，供无窗口测试使用。

persistence 不决定任何地下城规则，也不重新计算随机结果。

### 4.3 raylib 表现层

raylib Host 负责：

- 加载或首次创建稳定检查点。
- 驱动 DungeonSession。
- 在收到待保存事务后同步调用 persistence。
- 将保存结果明确回传 DungeonSession。
- 绘制元素门、生态主题、深渊效果、洞口和 HUD。
- 采集 E、N、F1、F12 等平台输入。

combat 继续不依赖 dungeon 或 persistence。dungeon 可以使用 combat 作为当前房战斗实现，但不得把地下城规则反向放入 combat。

## 5. 稳定数据模型

### 5.1 DungeonRules

规则配置至少包含：

- 四元素基础权重：100、100、100、100。
- 每偏向点权重增量：25。
- 洞口阈值：1000 / 10000。
- 深渊阈值：100 / 10000。
- 规则版本：1。

配置在创建新局和加载存档时验证。阈值必须位于 0 至 10000，基础权重必须大于 0，权重计算必须检查整数溢出。

### 5.2 DungeonRunState

稳定运行状态至少包含：

- 64 位根种子。
- 64 位存档提交代数。
- 64 位全局房间序号，内部从 0 开始。
- 64 位地下城深度，对玩家从 1 开始。
- 64 位本层房间序号，对玩家从 1 开始。
- 四个 32 位无符号偏向点数。
- 当前 RoomDescriptor。
- 最近一次已提交切换类型与方向。

偏向点与全部 64 位计数都使用检查增加，不允许回绕。被选择的偏向点、存档提交代数、全局房间序号、深度或本层房间序号达到上限时拒绝继续切换，保留当前已清房状态并进入明确故障状态。

### 5.3 RoomDescriptor

每个实际房间只保存一个描述：

- 全局房间序号。
- 房间种子。
- 深度和本层房间序号。
- 进入侧。
- 主生态。
- 是否有普通洞口。
- 是否为深渊。

固定战斗模板不是 RoomDescriptor 的持久字段。运行时只根据进入侧和规则版本派生 CombatLabConfig，不把浮点战斗配置或战斗快照写入存档；加载后的房间阶段固定从 Locked 开始。

未选择的三个门不派生种子、不投掷随机、不生成描述，也不保存候选结果。

### 5.4 PendingTransition

待提交事务包含：

- 请求类型：元素门或下坠。
- 元素门方向；下坠时方向为 none。
- 完整的下一 DungeonRunState。
- 预期的新提交代数。

PendingTransition 只存在于内存。它没有通过持久化验证前，当前房间和当前稳定状态不得销毁或替换。

## 6. 房间生成与独立随机流

### 6.1 房间种子

初始房种子只由根种子、初始房间序号和稳定域常量派生。

后续房种子只由当前房种子、下一全局房间序号、切换类型以及元素方向派生。切换类型稳定 ID 为 door=0、descent=1；方向稳定 ID 为 up=0、down=1、left=2、right=3、none=255。下坠使用独立域和 none，不与任何元素门共享方向输入。

规则版本 1 固定复用 core::DeterministicRng：SplitMix64 扩展四个初始状态，xoshiro256** 产生 64 位输出，derive_stream 使用现有 SplitMix64 域混合。对应算法、移位、旋转和乘法常量都属于规则版本，禁止在不提升规则版本和提供迁移的情况下改变。

规则版本 1 固定使用以下 64 位域：

- 初始房：0x524F4F4D5F494E49。
- 元素门后房：0x524F4F4D5F4E4558。
- 下坠后房：0x44455343454E5431。
- 生态：0x45434F4C4F475931。
- 洞口：0x484F4C455F563031。
- 深渊：0x41425953535F3031。

定义 First(seed, id) 为 derive_stream(seed, id).next_u64()。规则版本 1 的完整组合顺序固定为：

- initial(root, serial) = First(First(root, initial_domain), serial)。
- door(current, next_serial, direction) = First(First(First(current, door_domain), next_serial), direction_id)。
- descent(current, next_serial) = First(First(First(current, descent_domain), next_serial), none_id)。

所有运算都按 uint64_t 模 2^64 语义执行。生态累计区间顺序固定为火、水、电、混沌，样本落入左闭右开区间。禁止依赖指针、时间、渲染帧、容器遍历顺序或标准库随机分布。

规则版本 1 固定以下独立黄金向量：

| 输入或步骤 | 期望值 |
| --- | --- |
| 根种子 | 0x0123456789ABCDEF |
| initial(root, 0) | 0xCA5A07A71C3153C4 |
| 从上一步 door(..., 1, up) | 0xCF92F9DC3E32DA47 |
| 从上一步 door(..., 2, right) | 0xF71A3E545FA8D5CC |
| 从上一步 descent(..., 3) | 0x21DD351FA20839E8 |

对房间种子 0xCF92F9DC3E32DA47，生态权重为 125、100、100、100 时，生态样本必须为 83 并选择火；洞口万分样本必须为 7295；深渊万分样本必须为 8629。

### 6.2 三个房间随机流

得到房间种子后，再分别派生：

- ecology 域：按四元素整数权重选择主生态。
- hole 域：生成 0 至 9999 的无偏整数，小于 1000 时有洞。
- abyss 域：生成 0 至 9999 的无偏整数，小于 100 时为深渊。

所有有界整数使用固定拒绝采样：令 threshold = (-bound) mod bound，丢弃小于 threshold 的 64 位输出，再返回 output mod bound。生态抽取也使用该方法映射到权重总和，禁止使用 std::uniform_int_distribution。

三个流互不消费彼此状态。修改元素偏向只能改变 ecology 结果，不能改变同一房间种子的洞口或深渊结果。洞口与深渊可以同时为真。

### 6.3 元素门切换

选择元素门时按以下顺序构造下一稳定状态：

1. 检查所有计数是否可以安全递增。
2. 全局房间序号加 1。
3. 本层房间序号加 1。
4. 对应元素偏向检查后加 1；已到上限则进入故障状态，不生成事务。
5. 使用更新后的偏向生成唯一下一房。
6. 深度保持不变。

偏向增加立即影响下一房生态权重。

### 6.4 下坠切换

只有当前房间有洞、房间已清理、玩家在提示范围且按下 E 时才能提出下坠：

1. 检查全局房间序号和深度能否安全递增。
2. 全局房间序号加 1。
3. 深度加 1。
4. 本层房间序号设为 1。
5. 四元素偏向全部清零。
6. 使用零偏向生成新层首房。

下坠不增加任何元素偏向。

## 7. 生命周期与事务协议

RoomPhase 在 Stage 2 状态上增加 Committing 与 Faulted：

Locked → Combat → Cleared → AwaitingExit → Committing → Transitioning

任何阶段发生不可安全继续的规则、队列或提交不确定错误时进入 Faulted。Faulted 保留最后可显示快照和诊断，但停止战斗更新、输入提交、随机生成和存档切换；只能退出或重启后按磁盘稳定状态恢复。

### 7.1 门请求

AwaitingExit 时，玩家位于开放门洞并继续向外移动，产生一次门请求。DungeonSession 构造 PendingTransition，冻结当前已清房战斗并进入 Committing。

### 7.2 洞口请求

洞口从进房时可见。Locked 与 Combat 阶段为封闭状态。Cleared 与 AwaitingExit 阶段点亮。玩家位于洞口提示半径内并按 E，且当前描述的 has_hole 为真时，产生一次下坠请求并进入 Committing。

清房后四扇元素门始终全部开放；存在洞口时，洞口是额外的第五个离开选项，不替代任何元素门。

### 7.3 保存成功

Host 将 PendingTransition 中的下一稳定状态写入目标存档槽。persistence 必须返回三态结果：

- committed：预期代数和预期有效载荷已经作为有效槽发布。
- not_committed：能够证明新状态没有发布，旧稳定槽仍是唯一可加载状态。
- indeterminate：已经跨过文件发布边界，但无法可靠判断磁盘上的最终状态。

committed 必须携带与 PendingTransition 完全匹配的代数和有效载荷摘要。DungeonSession 验证成功后：

1. 将下一状态设为内存稳定状态。
2. 发出 transition_committed。
3. 销毁旧 CombatWorld。
4. 发出 room_destroyed。
5. 进入 Transitioning。
6. 下一固定 Tick 构造新房战斗并回到 Locked。

### 7.4 保存失败

not_committed 时，DungeonSession 丢弃 PendingTransition，保持旧稳定状态和当前已清房 CombatWorld，返回 AwaitingExit 并发出 save_failed。玩家可以重新提出门或洞口请求。

indeterminate、错误代数或错误有效载荷摘要一律进入 Faulted，不允许返回旧房重选。Host 显示存档提交状态不确定并要求退出或重启；重启时重新扫描双槽并采用磁盘上可证明的最新稳定状态。

### 7.5 崩溃窗口

- 新槽尚未成为完整有效文件：启动时加载旧槽，恢复当前房间。
- 新槽已完整有效、内存尚未销毁旧房：启动时加载代数更高的新槽，直接进入下一房。
- 文件发布后发生 I/O 错误或回执丢失：当前进程进入 Faulted，不能回旧房；重启后由双槽扫描决定稳定状态。
- 新槽有效后，任何启动路径都不得加载旧槽让玩家重新选门。

### 7.6 重载和 R 重置

从稳定检查点加载时，使用已保存 RoomDescriptor 创建同一房间的初始战斗状态，不调用房间随机逻辑。

R 只重建当前房间战斗，不改变稳定检查点、房间种子、生态、洞口、深渊、深度或偏向，也不写入新提交代数。

## 8. 双槽存档

### 8.1 路径与文件

正式运行使用：

- %LOCALAPPDATA%\InfiniteDungeon\save\run_a.sav
- %LOCALAPPDATA%\InfiniteDungeon\save\run_b.sav

测试与可视验收可以通过 --save-dir 指定隔离目录。--seed 只在目标目录没有有效存档、需要创建新局时生效；已有有效存档优先，禁止用命令行种子覆盖。

### 8.2 文件格式

文件包含固定头和定长有效载荷：

- 8 字节魔数。
- 32 位格式版本。
- 32 位规则版本。
- 64 位提交代数。
- 32 位有效载荷长度。
- 32 位 CRC32。
- DungeonRunState 除提交代数外的固定宽度持久字段。

提交代数只编码在文件头中，解码后写入内存 DungeonRunState，不在有效载荷中重复。整数编码使用明确的小端顺序。布尔值只允许 0 或 1；枚举值必须位于已定义范围。CRC32 覆盖格式版本、规则版本、提交代数、有效载荷长度和全部有效载荷，不覆盖 CRC 字段本身。CRC32 用于检测损坏，不作为安全或防篡改机制。

### 8.3 写入协议

1. 选择目标槽：没有有效槽时使用 A；一个有效槽且另一槽缺失时使用缺失槽；两个有效槽且代数不同时使用较低代数槽；两个有效槽同代数且载荷相同时固定把 A 视为当前槽、B 视为下一目标槽。
2. 一个有效槽且另一槽损坏时，先把损坏槽改名归档；归档成功后复用其固定槽位，归档失败则进入阻塞错误。
3. 在同目录写入临时文件。
4. flush 并关闭。
5. 重新打开临时文件并完整解码、校验版本、长度、枚举、范围和 CRC。
6. 删除旧的非当前目标槽；当前有效槽始终保留。
7. 将临时文件重命名为目标槽，这一步是文件发布边界。
8. 重新扫描两个最终槽，不依赖内存中的预期结果直接判定。
9. 若预期代数和有效载荷摘要已成为有效最新槽，返回 committed。
10. 若能够证明发布未发生或目标文件明确无效并已隔离，同时旧槽仍是唯一有效槽，返回 not_committed。
11. 发布边界后出现读取失败、状态冲突或无法证明磁盘真值时返回 indeterminate。

临时文件、截断文件和 CRC 错误文件都不能参与最高代数选择。

### 8.4 启动加载

- 两槽均有效且代数不同：选择提交代数更高者。
- 两槽均有效且代数相同：有效载荷完全相同时固定选择 A 为当前槽、B 为下一目标槽；有效载荷不同时视为冲突并进入阻塞恢复画面。
- 仅一槽有效、另一槽缺失：加载有效槽，下一次保存创建缺失槽。
- 仅一槽有效、另一槽损坏：先归档损坏槽；成功后加载有效槽并显示已从备份恢复提示，失败则进入阻塞恢复画面。
- 两槽均不存在：从 OS 随机源创建一次 64 位根种子，生成并成功保存初始房间后进入游戏。
- 只要目录中存在任一存档槽或临时文件、但没有有效槽：进入阻塞恢复画面，不创建或覆盖新存档。

阻塞恢复画面按 N 后，将所有损坏槽和临时文件改名为带 UTC 时间戳的备份，再创建并保存新局。任一步失败都保留错误画面，不删除尚未成功归档的文件。

## 9. raylib 表现与操作

### 9.1 元素门

| 门 | 主题色 | 标签 |
| --- | --- | --- |
| 上 | 橙红 | FIRE |
| 下 | 蓝 | WATER |
| 左 | 黄青 | LIGHTNING |
| 右 | 紫绿 | CHAOS |

Locked 与 Combat 阶段保留元素门框但显示不透明阻挡。Cleared 与 AwaitingExit 阶段移除阻挡并显示方向箭头和元素标签。

### 9.2 生态主题

当前主生态改变地面、远景和边框的低饱和色调。生态主题不能改变碰撞、战斗数值、洞口概率或深渊概率。

深渊房在生态主题上叠加：

- 紫红色环境脉冲。
- 屏幕边缘暗化。
- 常驻 ABYSS HUD 标记。

Stage 3 不播放专属深渊奖励流程，也不替换三个测试目标。

### 9.3 洞口

洞口固定在房间下半部中央。Stage 3 表现配置默认中心世界坐标为 {0.0, 2.0, 0.0}，默认交互半径为 1.20；两者属于集中式表现参数，不属于永久地下城规则。

- Locked 与 Combat：暗色封闭环，不显示交互提示。
- Cleared 与 AwaitingExit：点亮并缓慢脉冲。
- 玩家与中心的 X/Y 平面距离不超过配置交互半径时显示 E - Descend。
- E 使用按下沿，只提交一次；长按不能跨房重复触发。
- 没有洞口的房间不绘制洞口，也不接受 E。

### 9.4 HUD 与按键

普通 HUD 显示：

- Depth 与 Floor Room。
- 当前主生态。
- Fire、Water、Lightning、Chaos 四偏向点。
- ABYSS 状态。
- Hole: NONE、SEALED 或 READY。
- Autosave: SAVING、SAVED、RECOVERED 或 ERROR。

F1 追加显示根种子、房间种子、全局房间序号、三项随机结果、存档槽、提交代数和全部溢出诊断。F12 保存 stage3-dungeon-rules.png。

按键保持：

- WASD：移动。
- J：三段普通攻击。
- K：跳跃。
- L：上挑。
- E：洞口下坠。
- R：重置同一房间战斗。
- F1：诊断信息。
- F12：截图。
- Esc：退出。
- N：仅在没有可加载稳定存档或双槽发生冲突的阻塞恢复画面确认归档并新建存档。

## 10. 错误处理

- 非法规则配置：拒绝创建会话，显示配置错误。
- 存档代数、房间序号、深度或本层房间序号溢出：保留最后快照并进入 Faulted，禁止回绕。
- 被选择偏向达到 32 位上限：拒绝事务并进入 Faulted，不继续生成房间。
- 权重总和无法安全表示：拒绝生成下一房并进入 Faulted。
- 地下城或战斗事件队列溢出：记录诊断并立即进入 Faulted；调试构建额外触发断言，Release 同样停止传播错误状态。
- 文件发布边界前且可证明未提交的写入失败：返回 AwaitingExit，不销毁当前房。
- 文件发布边界后的不确定错误：进入 Faulted，不能回旧房重选。
- 单槽损坏：先归档损坏槽，再使用另一有效槽；归档失败则阻塞。
- 双槽损坏或版本均不支持：进入 N 确认的阻塞恢复画面。
- 归档损坏文件失败：不开始新局，不删除原文件。
